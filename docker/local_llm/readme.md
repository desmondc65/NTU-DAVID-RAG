# Local LLM Deployment Deep Dive (llama.cpp + Docker + NVIDIA GPUs)

This folder runs a **local OpenAI-compatible LLM endpoint** using:

- `ghcr.io/ggml-org/llama.cpp:server-cuda`
- a large GGUF model mounted from host disk
- NVIDIA GPUs exposed to Docker
- an HTTP API on port `8000` (by default)

The current default setup in this folder is tuned for:

- **Model**: `Qwen2.5-VL-72B-Instruct-Q4_K_M.gguf`
- **Vision projector (optional but enabled by default)**: `mmproj-F16.gguf`
- **GPU strategy**: split across two GPUs (`NVIDIA_VISIBLE_DEVICES=1,2`, `TENSOR_SPLIT=1,1`)
- **API compatibility**: OpenAI-style `POST /v1/chat/completions`

## 1) What This Service Does

When running, this service:

1. Starts a Docker container with CUDA-enabled llama.cpp server image.
2. Verifies GPU runtime is really available inside the container.
3. Verifies model files exist in mounted host path.
4. Builds llama.cpp server arguments from `.env` values.
5. Launches the server and exposes:
	 - health endpoint: `GET /health`
	 - OpenAI-compatible API base: `/v1`
6. Writes logs to both:
	 - `docker logs qwen3-vl-server`
	 - `docker/local_llm/log.txt` on host

This gives your pipeline a local endpoint that behaves like an OpenAI endpoint while keeping inference fully on your machine.

## 2) Files In This Folder

- `.env`

- `log.txt`

## 3) Architecture and Request Flow

### 3.1 Runtime layers

- **Host**
	- stores model files under `MODEL_DIR`
	- runs Docker Engine + NVIDIA Container Toolkit
- **Container**
	- runs llama.cpp server binary (`llama-server`, `/app/llama-server`, or `llama-cli` fallback)
	- loads GGUF model from mounted `/models`
- **Client code in this repo**
	- `utils/llm_clients/local_llm.py` uses OpenAI SDK with a local base URL
	- default base URL expected by code: `http://localhost:8000/v1`

### 3.2 Endpoints

- Liveness: `http://localhost:8000/health`
- OpenAI-compatible API root: `http://localhost:8000/v1`
- Common route: `POST /v1/chat/completions`

### 3.3 Authentication model

- llama.cpp server checks bearer token using `LLAMA_API_KEY`
- this compose maps it from `.env` variable `LOCAL_LLM_API_KEY`
- repository clients also default to `LOCAL_LLM_API_KEY=local-dev-key`

Keep API key values aligned between server `.env` and client runtime env to avoid 401/403-style failures.

## 4) Prerequisites (Hard Requirements)

1. Linux host with NVIDIA GPUs.
2. NVIDIA driver working on host (`nvidia-smi` succeeds).
3. Docker Engine + Compose v2.
4. NVIDIA Container Toolkit configured so GPUs are visible in Docker.
5. Enough disk for model files (Q4_K_M ~42 GB + mmproj ~1.5 GB).
6. Enough VRAM for target context and throughput settings.

Quick pre-checks:

```bash
nvidia-smi
docker --version
docker compose version
```

GPU check inside Docker:

```bash
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
```

If the command above fails, fix Docker GPU runtime first. The local LLM container will not run correctly without it.

## 6) Environment Configuration (`.env`) Explained

Current `.env` values are already suitable for this folder setup, but each variable matters:

- `MODEL_DIR`
	- absolute host path containing model files
	- mounted into container as read-only `/models`
- `MODEL_FILE`
	- GGUF filename under `MODEL_DIR`
	- compose startup script exits with clear error if missing
- `MODEL_ALIAS`
	- model name exposed via OpenAI-compatible API
	- clients should use this as `model` field
- `SERVICE_PORT`
	- host port mapped to container `8000`
- `LOCAL_LLM_API_KEY`
	- bearer token required by server
	- must match client API key
- `TENSOR_SPLIT`
	- how tensors are distributed across visible GPUs
	- for 2 GPUs, `1,1` is equal split
- `CTX_SIZE`
	- context window tokens; very large contexts increase memory pressure
- `BATCH_SIZE`, `UBATCH_SIZE`
	- inference batching knobs affecting throughput/memory tradeoff
- `THREADS`
	- CPU threads for host-side work
- `PARALLEL`
	- number of parallel request slots on server
- `MM_PROJ_FILE`
	- vision projector file to enable image input for VL models
	- if empty, server starts in text-only mode

## 7) Docker Compose Deep Explanation

### 7.1 Service identity

- service name: `qwen3-vl-server`
- container name: `qwen3-vl-server`
- image: `ghcr.io/ggml-org/llama.cpp:server-cuda`

### 7.2 GPU controls

Multiple layers are used to force GPU scheduling and visibility:

- `gpus: all` requests GPU runtime support
- `deploy.resources.reservations.devices` pins to GPU device IDs `1` and `2`
- env variables `NVIDIA_VISIBLE_DEVICES=1,2` and `CUDA_VISIBLE_DEVICES=1,2` narrow visible devices in container

This defensive approach reduces accidental CPU fallback and keeps workload on intended GPUs.

### 7.3 Preflight checks before server launch

Container startup command performs checks and exits early on failure:

1. `nvidia-smi` exists in container
2. GPUs are detectable (`nvidia-smi -L`)
3. at least two GPUs are visible
4. `MODEL_FILE` is set
5. `/models/$MODEL_FILE` exists

These checks make failures explicit and easier to diagnose from logs.

### 7.4 llama.cpp server argument mapping

The command constructs:

- `--model /models/$MODEL_FILE`
- `--alias $MODEL_ALIAS`
- `--n-gpu-layers 999` (offload as many layers as possible)
- `--tensor-split $TENSOR_SPLIT`
- `--ctx-size $CTX_SIZE`
- `--batch-size $BATCH_SIZE`
- `--ubatch-size $UBATCH_SIZE`
- `--threads $THREADS`
- `--parallel $PARALLEL`
- `--flash-attn $FLASH_ATTN` (default `auto`)
- `--jinja`
- optional `--mmproj /models/$MM_PROJ_FILE`

### 7.5 Binary path compatibility fallback

Different llama.cpp image tags expose binaries differently. Startup checks in this order:

1. `llama-server` in `PATH`
2. `/app/llama-server`
3. `llama-cli`

If none are found, container exits with code `127`.

### 7.6 Logging strategy

Server stdout/stderr is piped through `tee`:

- visible through `docker logs`
- persisted to `docker/local_llm/log.txt`

### 7.7 Healthcheck

Compose healthcheck probes `http://localhost:8000/health` every 30s after 60s start period.

## 10) Performance Tuning Guide

Large models are sensitive to context and batching. Adjust one knob at a time.

- If OOM or startup failure:
	- reduce `CTX_SIZE` first (largest memory lever)
	- then reduce `BATCH_SIZE`
	- then reduce `UBATCH_SIZE`
- If throughput is low but stable:
	- raise `BATCH_SIZE` gradually
	- increase `PARALLEL` carefully (can increase memory pressure)
- If latency is high for single requests:
	- keep `PARALLEL=1`
	- use moderate `BATCH_SIZE`
- If multi-GPU balance is uneven:
	- experiment with `TENSOR_SPLIT` values (for example `1,1`, `1.2,0.8` style ratios)

## 11) Troubleshooting Matrix

### 11.1 Container exits immediately with GPU error

Symptoms:

- log contains messages about missing `nvidia-smi` or no detected GPU

Actions:

1. Confirm host driver: `nvidia-smi`
2. Confirm Docker GPU runtime: `docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi`
3. Recheck NVIDIA Container Toolkit installation and daemon config

### 11.2 Model not found error

Symptoms:

- log shows `Model file not found: /models/...`

Actions:

1. Confirm `.env` `MODEL_DIR` absolute path
2. Confirm `.env` `MODEL_FILE` exact filename
3. Confirm file is present on host and readable

### 11.3 Health endpoint fails

Symptoms:

- `curl /health` fails or times out

Actions:

1. inspect `docker logs qwen3-vl-server`
2. inspect `docker/local_llm/log.txt`
3. wait for initial model load (can take significant time for large GGUF)

### 11.4 API auth errors

Symptoms:

- requests return auth failures

Actions:

1. match bearer token to `.env` `LOCAL_LLM_API_KEY`
2. ensure client env and server env use same key

### 11.5 Wrong model name in requests

Symptoms:

- API rejects unknown model

Actions:

1. use `.env` `MODEL_ALIAS` in request payload `model`
2. if using repo client defaults, pass explicit `model_name` to avoid alias mismatch

## 13) Security and Operations Notes

- `privileged: true` and GPU access provide broad device capabilities; restrict host access accordingly.
- API key in this setup is intended for local/LAN trust boundary, not internet exposure.
- Do not expose port `8000` publicly without proper reverse proxy, TLS, and stronger auth.
- Keep model directory mounted read-only as currently configured (`:ro`) to reduce accidental writes.

## 15) Gemma 4 31B Service (Transformers)

This folder now also includes a dedicated Gemma service:

- Compose file: `docker-compose.gemma4-31b.yml`
- App server: `gemma_server/app.py`
- Runtime: FastAPI + Hugging Face Transformers `pipeline(task="any-to-any")`

It exposes an OpenAI-compatible endpoint at:

- `POST /v1/chat/completions`
- `GET /v1/models`
- `GET /health`

### 15.1 Configure `.env`

Set/confirm these variables in `.env`:

- `GEMMA_MODEL_ID` (default: `google/gemma-4-31b-it`)
- `GEMMA_MODEL_ALIAS` (default: `gemma4-31b-it`)
- `GEMMA_DTYPE` (`bfloat16` recommended on modern GPUs)
- `GEMMA_MAX_NEW_TOKENS`
- `HUGGING_FACE_HUB_TOKEN` (required for gated/private models)
- `HF_CACHE_DIR` (persistent model cache on host)

### 15.2 Start / Stop

```bash
cd docker/local_llm

# Start Gemma service
docker compose --env-file .env -f docker-compose.gemma4-31b.yml up -d --build

# Check health
curl -fsS http://localhost:${SERVICE_PORT:-8000}/health

# Tail logs
docker logs -f gemma4-31b-server

# Stop
docker compose -f docker-compose.gemma4-31b.yml down
```
